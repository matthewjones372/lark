# 0125: lark-kafka on the Kafka 4.3 client

## Problem

`lark-kafka` is built against `kafka-clients` 3.8.0, and its tests run an
embedded 3.8 broker. The petshop moved its bus to avro4k's Confluent serde,
which needs Confluent 8.3, which is built on Kafka 4.3. So the petshop pins
the 4.3 client and runs `lark-kafka` on a client one major version newer than
the one it was compiled and tested against. It works, but nothing in Lark says
so, and the next consumer to need Confluent 8 has to find that out again.

A trial build on 4.3 shows the move is small. `lark-kafka`'s 39 tests and
`lark-kafka-pekko`'s 17 pass against an embedded 4.3 broker. One call no
longer compiles, because the build treats warnings as errors:
`ConsumerGroupMetadata(groupId)` in `Commits.kt` is deprecated for removal
since Kafka 4.2.

## Not doing

- Moving `lark-kafka-pekko` to Pekko's connector `2.0.0-M1`, the first that
  is built on Kafka 4. It is a milestone and needs Pekko 2.0 milestones. The
  connector stays on 1.1.0, and Gradle resolves its `kafka-clients` up to 4.3,
  which its tests pass on.
- Changing which group metadata a transaction commits with (spec 0124).
- Kafka 5.

## Shape

No API change. In the build:

```kotlin
// lark-kafka
api("org.apache.kafka:kafka-clients:4.3.0")
testImplementation("io.github.embeddedkafka:embedded-kafka_$scalaBinary:4.3.1")

// lark-kafka-pekko
testImplementation("io.github.embeddedkafka:embedded-kafka_$scalaBinary:4.3.1")
```

- `Commits.kt` keeps committing a leaving consumer's last transaction with
  the group id alone, as spec 0124 decided. The deprecated constructor is
  suppressed at that one call, with a comment saying why it stays and what
  replaces it: Kafka 5 makes `ConsumerGroupMetadata` an interface, which Lark
  can then implement with the group id alone.
- `docs/kafka.md` says `lark-kafka` now brings the 4.3 client, which a
  consumer on 3.x will be moved up to, and that Kafka 4 clients need a 2.1 or
  later broker. Lark keeps no changelog file, so this is where it is said.

## Why this shape

The deprecation's suggested replacement, `consumer.groupMetadata()`, is the
member's own metadata, and after the consumer has left the broker refuses it.
Using it would abort a run's last transaction on every clean stop, so the
last batch would be redone by whoever reads next. That is still exactly once,
but it turns a clean stop into a failed one. Holding the consumer open until
downstream drains was 0124's rejected alternative, and it is still rejected.
Recommended: suppress until Kafka 5 gives an interface to implement.

## Stack

- [x] **`spec-0125-kafka-4-3`** ([#348](https://github.com/matthewjones372/lark/pull/348)): `kafka-clients` 4.3.0 and embedded Kafka
      4.3.1 in both modules, the suppressed constructor with its reason, and
      the note in `docs/kafka.md`.
      Done when: `./gradlew :lark-kafka:check :lark-kafka-pekko:check` passes,
      with `lark-kafka-pekko` resolving `kafka-clients` 4.3.0.

## Acceptance

```bash
./gradlew :lark-kafka:check :lark-kafka-pekko:check
./gradlew :lark-kafka-pekko:dependencyInsight --configuration runtimeClasspath --dependency kafka-clients
```

Then the petshop, on the next Lark release, drops the comment explaining why
`lark-kafka` runs on a newer client. It keeps its `strictly("4.3.0")` pin,
since Confluent still asks for its own `8.3.0-ccs` build.

## Open questions

- **A breaking change for 3.x consumers?** A consumer pinned to a 3.x client
  would now get 4.3 unless they pin it back, and Kafka 4 dropped APIs Kafka 3
  had deprecated. Recommended: ship it in the next minor (0.11.0), with the
  move named in that release's notes, since Lark is pre-1.0 and the petshop
  is its consumer.
- **Connector 1.2.0?** It is the newest stable Pekko connector, on Kafka 3.9.
  It would change nothing here, since 4.3 wins resolution either way.
  Recommended: leave 1.1.0 and move straight to 2.0 when Pekko 2.0 is
  released, in its own spec.
